# Nautilus 节奏与谱号修复方案

**状态：** 方案设计，尚未实现

**日期：** 2026-07-31

**适用工具：** Sheet2Music

## 1. 背景

《ヨルシカ - ノーチラス.pdf》已经使用当前 600 DPI 页面渲染、上下裁剪和 GPU HOMR 流程转换。BPM 输入为 `80`，这一项在转换报告和 MIDI 中是正确的，但 MP3 在多个位置出现明显卡顿。

这份谱子还有两个结构特征：

- 第 25 小节为 `2/4`，第 26 小节恢复为 `4/4`；
- 第 14~16 小节左手使用高音谱号，第 17 小节恢复低音谱号；左手声部在这些位置较复杂。

## 2. 已确认的根因

### 2.1 当前拍号修复会覆盖合法变化

当前 `ConvertParams.time_signature` 是整首谱子的单一拍号，修复器也会对每个小节写入相同的 `time`。因此用户输入 `4/4` 后，第 25 小节的合法 `2/4` 无法表达。

当前 MIDI 修复器还会把所有拍号元数据压缩成从 tick `0` 开始的一个 `4/4` 事件。它只修改 MIDI 元数据，不修改音符的 tick 时序，因此不能修复由 MusicXML 时间布局造成的卡顿。

### 2.2 HOMR 输出存在未修复的声部时序

本次转换报告中有 80 个小节，其中 26 个小节被标记为 `unsupported`。当前修复器遇到以下情况会放弃重建：

- 小节中含有 `forward`；
- 多声部的时值没有完全等于目标小节长度；
- `backup` 之后的声部游标不能安全重建。

这类小节会原样交给 MuseScore。MuseScore 需要自行解释超出小节长度、声部重叠或游标回退过度的 XML，最终可能生成间断、延迟或重叠的 MIDI 事件。

当前实现用整个小节最后留下的游标值判断完整性，这对双谱表和多声部并不可靠。每个 `staff + voice` 必须独立计算局部时序。

### 2.3 当前谱号归一化范围过大

PDF 第 14 小节左手的高音谱号被 HOMR 识别到了，但第 15 小节被误识别为低音谱号，第 17 小节又没有输出新的谱号。当前修复器以整个 part/staff 的首个谱号为基线，并把报告中的左手第 10~76 小节整体归一化为高音谱号。

这种全局基线规则会把后续真实的低音谱号也改掉。并且修改 `<clef>` 只改变 MusicXML 的显示，不会自动修改已经写入 `<pitch>` 的 MIDI 音高。

### 2.4 第 25 小节需要边界级修复

PDF 第 25 小节明确显示 `2/4`，下一小节恢复 `4/4`。HOMR 第 3 页的首个 MusicXML 小节对应全谱第 25 小节，但不同声部的导出时长不一致，说明这里可能不只是漏写 `<time>`，还可能存在跨拍号边界的声部合并。

因此仅把第 25 小节的 `<time>` 改成 `2/4` 不足以保证播放正确，需要使用已知的小节边界重新整理该处的声部事件。

## 3. 目标与非目标

### 目标

1. 支持整谱默认拍号以及按小节声明的拍号变化。
2. 保留第 25 小节的 `2/4`，并在第 26 小节恢复 `4/4`。
3. 在系统边界和声部范围内修复谱号，不再使用跨全曲的单一谱号基线。
4. 处理合法的多声部 `backup/forward` 布局，减少 MuseScore 的自动纠错。
5. 通过 MusicXML、MIDI、PNG 和报告同时验证结果，而不是只依赖听感。
6. 保持保守规则：普通小节不因为时值超出就自动把音符推到下一小节。

### 非目标

- 不对整首曲子进行统一八度平移。
- 不根据音频猜测每个音符的音高。
- 不删除无法确定为错误的音符。
- 不把 HOMR 本身的所有识别错误伪装成修复成功。

## 4. 推荐设计

### 4.1 引入谱面结构计划

在保持默认界面简单的前提下，增加一个可选的谱面结构配置。没有配置时继续使用默认 `4/4`；有变化的谱子使用旁车配置或高级界面字段。

示例：

```json
{
  "default_time_signature": "4/4",
  "time_signature_changes": [
    {"from_measure": 25, "to_measure": 25, "signature": "2/4"},
    {"from_measure": 26, "signature": "4/4"}
  ],
  "clef_overrides": [
    {"staff": 2, "from_measure": 14, "to_measure": 16, "sign": "G", "line": 2},
    {"staff": 2, "from_measure": 17, "to_measure": 24, "sign": "F", "line": 4}
  ],
  "key_signature": {"fifths": -5}
}
```

配置只声明谱面结构，不包含音符列表。这样可以把 PDF 中明确可见的结构变化告诉修复器，同时避免把某一首曲子的例外写死在通用代码里。

### 4.2 按小节应用拍号

MusicXML 修复器应根据每个全谱小节的结构计划计算目标长度：

```text
expected_ticks = divisions * beats * 4 / beat_type
```

只在拍号实际发生变化的小节写入新的 `<time>`。合并页面后使用全谱小节号应用配置，避免页面内局部小节号与全谱小节号混淆。

MIDI 修复器使用同一份结构计划，在对应小节起点写入合法的拍号事件，并删除 HOMR 自动产生的异常拍号事件。它不能再无条件写入单一 `4/4`。

### 4.3 按声部重建时间游标

重建流程分为四步：

1. 按 `staff + voice` 收集音符、休止符和和弦事件。
2. 计算每个声部的局部起点、终点和小节内占用长度。
3. 在声部内部保留原始音符起点；只重建声部之间的 `backup`，必要时生成明确的 `forward`。
4. 用目标拍号验证每个声部的边界，并把无法确定的情况记录为结构警告。

对于第 25~26 小节，使用结构计划提供的明确边界切分跨边界事件。该操作只允许发生在显式声明的拍号边界，不能作为普通“超出小节就推进”的通用规则。

### 4.4 分系统处理谱号

谱号状态需要以系统和 staff 为范围维护：

- 系统开头明确输出的谱号优先级最高；
- 系统内部孤立的一小节相反谱号，只有在前后上下文都支持时才归一化；
- 不跨多个系统使用全曲首个谱号覆盖；
- 对 HOMR 遗漏的系统开头谱号，使用结构配置补充；
- 修复报告必须列出每个谱号覆盖的起止小节。

对于第 14~17 小节，第一阶段只确认 MusicXML 的谱号上下文。只有在 PNG 对照证明 HOMR 已经把音符按错误谱号写成错误绝对音高后，才允许添加指定范围的音高修正规则。谱号元数据修复和音高修复必须分开统计。

### 4.5 输出前后双重验证

转换报告新增以下验证结果：

- 每个小节、每个声部的目标时值与实际时值；
- 未处理小节及原因；
- 合法拍号变化列表；
- 谱号覆盖列表；
- MuseScore stderr 中的 `backup`、重叠和小节边界警告；
- 原始 MIDI 与修复后 MIDI 的时间签名、tempo、音符数量和总 tick。

MP3 必须从最终通过 MusicXML 验证的文件渲染。MIDI 元数据修复不能被当作 MusicXML 节奏修复的替代品。

## 5. 《ノーチラス》首个配置

实现时先使用以下结构作为回归样本：

```text
BPM: 80
默认拍号: 4/4
第 25 小节: 2/4
第 26 小节起: 4/4
左手第 14~16 小节: G clef / line 2
左手第 17 小节起: F clef / line 4
调号: -5 fifths
```

这份配置用于验证修复器的结构能力，不代表所有乐谱都使用相同的拍号、调号或谱号。

## 6. 实施顺序

1. 保留 raw MusicXML、fixed MusicXML 和 MuseScore 日志，即使用户只勾选 MIDI/MP3。
2. 为拍号变化和谱号覆盖增加数据模型、解析和报告字段。
3. 重写按声部的 MusicXML 游标检查与 `backup/forward` 重建。
4. 实现第 25~26 小节的显式边界切分，并增加单元测试。
5. 将 MIDI 拍号修复改为使用小节结构计划。
6. 实现按系统的谱号状态机和局部覆盖。
7. 对第 14~16 小节生成 PNG，确认是否需要额外音高修正。
8. 用 MuseScore 重新渲染 MIDI/MP3，检查日志和试听片段。
9. 将该谱子的结构配置加入回归测试，确认没有破坏默认 `4/4` 流程。

## 7. 验收标准

- 第 25 小节在 MusicXML PNG 中显示 `2/4`，第 26 小节显示 `4/4`。
- MIDI 只包含声明的拍号变化，不出现 `9/8、17/16、19/16` 等异常拍号。
- 第 14~16 小节左手显示高音谱号，第 17 小节恢复低音谱号。
- 第 14~17 和第 25~26 小节不再出现 MuseScore 小节游标警告。
- MP3 对应片段不再出现由 MusicXML 时间布局引起的卡顿。
- 修复报告明确区分：结构修复、谱号修复、音高修复和仍未解决的 HOMR 识别错误。
